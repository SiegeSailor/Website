# Three-Repo Profile Split — Design

**Date**: 2026-09-13
**Status**: Approved for planning
**Scope**: `SiegeSailor/Website`, `SiegeSailor/SiegeSailor`, `SiegeSailor/Claude-Plugins`

## Context

Today a single repository holds the website, the authored content, and a build
system that renders that content into four outputs. `source/content/resume/`
carries routing metadata — `consumers:`, `archived:`, `heading:` — and two
hand-synchronised loaders (`source/tooling/scripts/load-content.mjs` and
`source/website/helpers/server/content.ts`) filter it per output.

The metadata is maintenance the owner no longer wants. Selection is judgment
work, and an LLM now does it. This design removes the tagging system and the
loaders, and splits the remaining concerns across three repositories.

## Goals

1. `SiegeSailor/Website` contains the website and nothing else.
2. Profile facts live in `SiegeSailor/SiegeSailor`, beside the README they
   generate, and are read and written only by the owner and Claude.
3. Resume and README generation become skills, not build scripts.
4. No per-node routing metadata survives. No loader survives.
5. Verified facts cannot be silently reworded on their way into a document.

## Non-Goals

- Reworking the site's visual design or its routes.
- Changing the AWS/Terraform deployment topology.
- Preserving the `.docx` byte-for-byte across the migration.
- Automating resume tailoring end to end; a human approves each document.

## Target Architecture

```
SiegeSailor/SiegeSailor  (public)   profile/*.yaml  +  2 local skills  ->  README.md, resume .docx/.pdf
         |
         |  gh api, on demand
         v
SiegeSailor/Website      (public)   settings/content.ts  +  articles/*.md  ->  static site
```

```
SiegeSailor/Claude-Plugins (public)  conventional-commit plugin  ->  installed globally
```

Three repositories, one direction of data flow, no shared build system.

### Changes

**Flatten.** `source/website/*` moves to the repository root. `package.json`
loses its `workspaces` key and becomes the Next.js application's own manifest.
Path aliases, `tsconfig.json`, `eslint.config.mjs`, `.prettierignore`,
`.lintstagedrc.mjs`, and the workflow `paths:` filters all follow.

**`articles/` moves to the root** and keeps its existing loader,
`helpers/server/article.ts`. This is a genuine build input: `next build` reads
these files. It is unaffected by the removal of the content tagging system,
which it never used.

**`settings/content.ts` is new.** A single committed TypeScript module holding
everything the site renders that is not an article: identity, profile headline
and status, summary prose, project list with resolved versions, media links,
route titles, and site metadata. Plain typed constants — no YAML, no parsing,
no filesystem access, statically exportable.

Its first line records provenance:

```ts
// Generated by the update-website skill from
// SiegeSailor/SiegeSailor@<sha> on <date>. Do not edit by hand.
```

**Website-only configuration never leaves this repo.** `routes.yaml` and
`site-identity.yaml` describe the site, not the person, so they do not move to
`profile/`. Their content is authored directly into `settings/content.ts`.

### Deployment

`main-deploy.yml` loses the `Generate resume documents` step and its Docker
dependency. It checks out, installs, verifies, runs `next build`, and deploys
to S3 behind CloudFront exactly as before. No LibreOffice, no fonts, no
snapshot pinning in CI.

### Release Configuration

`release.config.mjs` and semantic-release stay. The root `package.json` version
is no longer stamped into any document, so `build-resume.mjs`'s read of it is
dropped on the way into the skill. The `.claude/rules/` files that reference
workspaces or npm script aggregation — `npm-script.md`, `workflow.md`,
`conventions.md` — are reviewed and updated for the single-package layout.

### Résumé Download Link

The `resume` entry in `media.yaml` and the `resume: FileDownIcon` mapping in
`settings/icons.ts` are both removed. The site links GitHub and LinkedIn only.
Nothing serves `/documents/JinYu-Zhang-Resume.pdf` after this change.

### Content Migration

Every file arrives from `source/content/resume/` with its envelope keys
stripped: `consumers:`, `heading:`, and `archived:` are all removed. The facts,
the inline comments explaining them, and the file boundaries are preserved
verbatim.

`schema.yaml`, `example.yaml`, and `e.yaml` are deleted. They exist to serve a
validation system this design removes.

`routes.yaml` and `site-identity.yaml` do not migrate; see Repository 1.

### What Happens to `archived: true`

The flag currently serves two unrelated purposes, which separate cleanly:

**Page-fit archiving** — most of the 14 archived nodes in `experience.yaml`,
3 entries in `summary.yaml`, the split skill rows, some education detail, the
second MIT and NYU certificates, and the whole of `activities.yaml` and
`publications.yaml`. These were held back because the resume must
fit one page. They become ordinary content. Fitting the page is now the resume
skill's job, and having more material to choose from makes it better at that,
not worse.

**Policy archiving** — StageSource, DY Game, and Servicetech's internship row.
These were held back for reasons that have nothing to do with space, and those
reasons must survive. They move to `POLICY.md` as prose.

### `profile/POLICY.md`

States, in plain English, the judgment calls that the tags used to encode. It
is read by both local skills and by the website skill. Its required contents:

1. StageSource was a Boston University course team working a real client's
   requirements. It prints as a detail of the M.S., never as employment — no
   employment-verification vendor should be sent after a job that was never one.
2. DY Game was an internship taken during the B.F.A. It prints under that
   degree, on the same reasoning.
3. Servicetech's stacked role lines are deliberate. Never widen the 2017–2018
   range to absorb the 2016–2017 internship; print the internship as its own
   line or omit it.
4. CooperSurgical's stacked role lines are deliberate, on the same reasoning:
   background-check vendors verify titles and dates separately.
5. The Shopee retention figure means first-to-last-day within a single 3–14 day
   festival run. It is not D1 or D7 cohort retention and must not be compressed
   to "player retention".
6. Contact details — phone number and postal area — belong on the resume
   document only. They never appear on the website or in the README.
7. Every fact here is verified and read by background-check vendors. No date,
   title, ranking, or number changes without explicit confirmation from Ken.

### `update-readme` Skill

Triggers on requests to update or sync the GitHub profile README.

1. Read `profile/` and `POLICY.md` from the working directory.
2. Resolve each GitHub project's latest release via `gh api`, falling back to
   its tag list, then to no version chip. Network failure is not fatal.
3. Compute total experience from `timeline.yaml` applied to today's date. Never
   print a stated figure.
4. Compose `README.md`: identity, headline, status line, summary, projects
   ordered Production before Development with Planning hidden, and media links.
5. Show the diff against the current `README.md` and write on confirmation.

Markdown output, so the verbatim check is advisory: differences are reported,
not blocking.

### `generate-resume` Skill

Triggers on requests to generate or tailor a resume.

Inputs: page limit (default 1), target audience, required sections, and any
posting or requirement text.

1. Read `profile/`, `POLICY.md`, and `reference/layout.md`.
2. Produce a **plan**: ordered sections, and for each, the exact strings
   selected from `profile/`.
3. `verify-verbatim.mjs` normalises whitespace and checks every string in the
   plan against the source files. A string found verbatim passes. A string not
   found is reported beside its nearest source match and requires explicit
   confirmation before rendering. This replaces node ids; nothing is maintained
   per node.
4. `build-resume.mjs` renders the approved plan to `.docx` using the `docx`
   library, following `reference/layout.md`.
5. `check-pages.mjs` converts with `soffice --headless` and asserts the page
   count with `pdfinfo`. Over the limit, the lowest-ranked selections are
   dropped and the document is re-rendered.
6. Output lands in the working directory. No run history is kept — "tracking"
   means the skill always reads the newest `profile/`, which is local.

If `soffice` or `pdfinfo` is missing, the skill reports that the page count is
unverified rather than exiting successfully in silence. The current Docker
build's page check fails silently in exactly this way and that behaviour is not
carried forward.

### `reference/layout.md`

The document-format constraints, as distinct from content policy:

- One US-Letter page unless the request overrides it.
- ATS-safe: single column; no tables, text boxes, headers, or footers.
- Standard section names: Summary, Skills, Work Experience, Education,
  Certifications.
- Section order is fixed and ATS-sensitive.
- Bullets come from the numbering configuration as native Word bullets. Never
  emit a literal `•`.
- Dates are right-aligned with a right tab stop and a literal tab in the run,
  never with spaces. LibreOffice ignores the docx `PositionalTab`.
- Calibri; sizes in half-points, spacing and indents in twips.
- `.docx` is the primary deliverable; the `.pdf` is a convenience.

### `package.json`

Private, not published. Dependencies: `docx` and `js-yaml`. `.gitignore`
excludes `node_modules/` and generated resume output.

```
Claude-Plugins/

│   └── skills/conventional-commit/SKILL.md

```

`marketplace.json` names the marketplace `siegesailor` and lists the plugin
with a relative source, `./plugins/conventional-commit` — the form the official
Anthropic marketplace uses for plugins living in the same repository.

### `conventional-commit` Skill

A generic port of the current `.claude/skills/commit/SKILL.md`, with this
repository's specifics removed:

- One Conventional Commits line, no body, no footer, under 72 characters.
- Imperative mood, lowercase subject, no trailing period.
- One concern per commit; split by concern, not by file.
- Type-to-release table for repositories running semantic-release.
- A major version is a human's call; prompt before wiring `!`.
- Never bypass a failing hook with `--no-verify`.
- Read the host repository's `CLAUDE.md` for its scope list and release
  configuration when one exists; take no scope when it does not.

Installed once with `/plugin marketplace add SiegeSailor/Claude-Plugins`, it
serves all three repositories and any other project.

## The `update-website` Skill

Lives in `SiegeSailor/Website` at `.claude/skills/update-website/`. Triggers on
requests to refresh the site from profile data or to change what a page shows.

1. Fetch `profile/` from `SiegeSailor/SiegeSailor@main` via `gh api`, recording
   the commit SHA.
2. Read `POLICY.md` and honour it — in particular, contact details never reach
   the site.
3. Resolve project versions via `gh api` and bake them into the output. Chips
   freeze between skill runs; this is accepted.
4. Rewrite `settings/content.ts`, stamping the source SHA and date.
5. Apply any structural instruction given alongside: a new section, a reordered
   page, a new profile file that needs a surface.
6. Report what changed and leave the commit to the owner.

The skill also encodes what a contributor must know: everything under `app/`
stays statically exportable; `settings/content.ts` is generated and not
hand-edited; a new media entry needs a matching icon in `settings/icons.ts`
before the site will render it.

## Migration Sequence

Each step leaves every repository in a working state.

1. **Seed `SiegeSailor/SiegeSailor`.** Copy `source/content/resume/*.yaml` to
   `profile/`, strip envelope keys, write `POLICY.md` and `profile/CLAUDE.md`.
   The Website repo is untouched and still builds.
2. **Port the resume builder.** Move `build-resume.mjs` and the page check into
   `.claude/skills/generate-resume/`, add `verify-verbatim.mjs`, write
   `SKILL.md` and `reference/layout.md`, add `package.json`. Verify the
   generated `.docx` against the current one for layout parity.
3. **Port the README builder** into `.claude/skills/update-readme/`. Verify its
   output against the README the workflow currently produces.
4. **Build `Claude-Plugins`.** Marketplace manifest, plugin manifest, generic
   commit skill. Install and confirm it loads.
5. **Generate `settings/content.ts`** in the Website repo by hand from the new
   `profile/`, and switch every page to it. The old loader still exists at this
   point; the site must build and render identically.
6. **Delete the old world.** `source/content/`, `source/tooling/`,
   `helpers/server/content.ts`, the two rules files, the commit skill,
   `main-readme.yml`, the three scripts, the Docker files.
7. **Flatten.** `source/website/*` to the root; fix aliases, configs, and
   workflow path filters.
8. **Write `update-website`** and use it to regenerate `settings/content.ts`,
   confirming it reproduces the hand-written file from step 5.

Steps 1–4 touch only the two new repositories. The Website repo's own refactor
is steps 5–8, and step 5 is a pure no-op at the rendered-output level, which is
what makes step 6 safe.

## Risks and Accepted Trade-offs

| Risk                                                                          | Mitigation or acceptance                                                                                                   |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `settings/content.ts` drifts from `profile/`                                  | The stamped SHA makes staleness a one-command check. Accepted: the site is refreshed on demand, not on every profile edit. |
| An LLM reorders sections or re-derives a policy call differently between runs | `POLICY.md` states each call in prose; the resume skill reads it every run.                                                |
| An LLM rewords a verified fact into a document                                | `verify-verbatim.mjs` blocks it. Reworded lines require explicit confirmation.                                             |
| Version chips freeze between skill runs                                       | Accepted for a personal site; reversible by restoring a build-time script.                                                 |
| The site's summary and the resume's summary diverge                           | Both read the same `summary.yaml`; divergence requires a human approving a reworded line in one of them.                   |
| Resume layout regresses during the port                                       | Step 2 compares output against the current `.docx` before the old builder is deleted.                                      |
| Page-count check silently passes without LibreOffice                          | The new skill reports "unverified" instead of exiting 0.                                                                   |

## Verification

- The site builds and deploys from the flattened repo with no `source/`.
- Every page renders identical content to the pre-migration site.
- The generated README matches the one `main-readme.yml` produces today.
- A generated resume fits one US-Letter page, uses native bullets, contains no
  literal `•`, and contains no string absent from `profile/`.
- `verify-verbatim.mjs` rejects a deliberately reworded bullet.
- The commit plugin loads and produces a valid message in all three repos.
