Back to 1 year ago, I followed [Long-Term Support](/blog/2024-08-19) and [THE TWELVE-FACTOR APP](https://12factor.net/) to create a Docker image SDK for internal use. The goal was to have a single base image for multiple languages and services, including shared code and configurations. Ideally, developers would use it as a development container (see [Visual Studio Code Developing Inside a Container](https://code.visualstudio.com/docs/devcontainers/containers)) while using it as a sole base image. However, this approach led to a really bad DX and I turned from the major advocate to the biggest critic of my own work. When it was getting close to the end of this year, and there was another project just announced to use this image, I decided to go through a severely large refactor to fix these issues.

### Original Designs and Issues

Before the refactor, I first took a deep reflection of what I was trying to achieve with this image, and what turned out to be disasters. To be honest, they were not bad if looked at separately, but when combined together, they created a nightmare for developers:

- **One Repository**: The images sticked to the format `<repository>:<without-foo>-<without-bar>-<version>-<architecture>`
  - Dealing with complicated tags was a challenge. `<repository>:latest-<architecture>` was used for offline device testing all the time
- **One Source Environment Variables**: All variables were defined/captures in a single file
  - Developers had to read through a long list of variables to find what they needed, such as `$PATH_*` and `$PORT_*` variables
  - A lot of out-of-shelf programs don't provide environment variable substitution. An extra wrapper layer that runs after the entrypoint was needed
  - Variables must be explicitly defined/captured repeatedly for different languages
- **Semantic File Structure**: Customized install and configuration paths for different languages and services
  - Developers had to learn where things were installed and configured. For example, regardless of language, all libraries were installed to `/home/user/.local`, and all programs built from source were installed in `/home/package`, and all generated files were placed in `/home/dynamic`
  - IDEs didn't automatically pick up these paths
- **Configurable Build Options**: Supported `amd64` and `arm64` architectures, and installed and configured services based on build arguments (for example, `$WITHOUT_MQ` to exclude RabbitMQ and Avahi, and disable the dependent services)0
  - Increased the CI/CD complexity and time
  - Increased the complexity of Abstracted Docker management CLI
  - Extra setup and build flow for programs that weren't available on certain architecture registries
  - Some services were not compatible with certain architectures. Using a stale version became the only option
- **Abstracted Docker Management CLI**: A fully abstracted Docker management CLI to handle authentication, tagging, building, testing, generating artifacts, and mounting processes
  - Developers just did't have time to learn another CLI tool
  - It took time to even just mount an optional volume
- **Shared Code**: Provided shared code as an in-place library
  - Excessive setup to make shared code for different languages work similar. For example, Python's `$PYTHONPATH`, Node.js's `$NODE_PATH`, and CMake's `$CMAKE_PREFIX_PATH` (and other build files) had to be set properly. This hugely overcomplicated the build process
  - Development containers became the only option because pointing library code outside the container was way too complex
  - Even just a small change, developers had to go back to submit a MR to the base image, and use pin a debugging base image version in their own project image
- **Untracked Generated Hidden Files**: Generated files, like compiled protocol buffer definitions, were placed in a folder that is created during `docker build` and ignored in Git
  - Developers had no idea what the generated files were
  - IDEs didn't recognize these files
  - Developers had to manually check whether the generated files were updated by running a container

The worse part was they all combined together. For example, the image generates static documentation sites for each language's shared code using Sphinx, Proto-Gen-Doc, and JSDoc. Adding one port environment variable will require changes in the Docker management CLI, configuration files for each language and service, and their build/startup scripts. Besides all the issues mentioned, the biggest problem is the actual development container performance. It is just slow to see how IDE responds when working inside it. It looks perfect at the first glance, but overtime the time spent on waiting just kills the productivity.

## Retrospective

During the refactor, I found some principles that I should have followed from the beginning:

- Simple is the best
- Don't overly configure scripts and programs
  - Simply not to put values that are as same as defaults
  - Not all scripts need to be parameterized
- Keep things transparent and easy to understand
- Redundancy is not always bad
- DX is efficiency

### New Designs

The new project structure is still a monolithic Docker image SDK. However, it allow redundancy and flexibility for each service and language, and treats each module as a separate entity:

```plaintext {2}
└── 📁 docker-context
    └── 📁 [module]
    ├── .dockerignore
    ├── Dockerfile
    ├── [dependencies].txt
    ├── supervisord.conf
└── 📁 protobuf
    └── 📁 compiled
        └── 📁 [namespace]
        └── 📁 google
    └── 📁 source
        └── 📁 [namespace]
        ├── buf.yaml
        ├── compile.sh
    ├── .gitignore
    ├── .gitlab-ci.yml
    ├── CONTRIBUTING.md
└── 📁 scripts
    ├── docker-[command].sh
├── .[lin|test].yml
├── .env
├── .env.example
├── .gitignore
├── .gitlab-ci.yml
├── CONTRIBUTING.md
└── README.md
```

Each module comes with its own `.gitignore`, `CONTRIBUTING.md`, and `.gitlab-ci.yml`. They are entirely independent and can be developed on the host machine without starting a container, while able to communicate with services in a running container. All the effort they need to put in integrating with the base image is to make sure the root files in `docker-context/` are configured properly.

### Best Practices

The other lesson I learned is that following conventional best practices does help a lot. There are plenty of tools highlighting errors, warnings, and code smells. For example, the `protobuf/` folder followed below:

- [Proto 1-1-1 Best Practice](https://protobuf.dev/best-practices/1-1-1/) Variant (1-1-1 practice in one scoped file)

- [Shell Style Guide](https://google.github.io/styleguide/shellguide.html)
