While developing an embedded system that required MongoDB transactions in a Docker container, I encountered a misleading version mismatch error message that stopped me from starting the MongoDB server with the replica set. The issue happened when I tried to tune the MongoDB server configuration to troubleshoot some performance issues, which was basically disabling as much as possible the MongoDB server features to see if it would help with the performance.The servers, on Linux AMD64, macOS ARM64, and purpose-built Linux ARM64 board, raised different error messages, result codes, and behaviors, which made me spent extra time on debugging.

<!-- description -->

The project, where the issue was discovered, builds a Docker container to run multiple services. Here I list some relevant details:

- **MongoDB**: [4.4.15](https://www.mongodb.com/docs/v4.4/reference/configuration-options/#configuration-file)
- **Docker Engine**: [20.10.17](https://docs.docker.com/engine/release-notes/20.10/#201017)
- **Base Image**: [ubuntu:22.04](https://hub.docker.com/layers/library/ubuntu/22.04/images/sha256-965fbcae990b0467ed5657caceaec165018ef44a4d2d46c7cdea80a9dff0d1ea?context=explore)

:::default
According to [MongoDB community discussions](https://www.mongodb.com/community/forums/t/mongodb-and-the-pi-4-on-ubuntu-64-bit-aka-armv8-0-a-support/220635/4), MongoDB versions 6+ and 8+ don't work reliably on certain ARM64 boards. This forced a downgrade to MongoDB `4.4.15`.
:::

## Previously Proven Working Solution

The MongoDB server was previously working correctly with the following configuration:

```conf title="mongod.conf"
storage:
    dbPath: /var/lib/mongodb
    engine: wiredTiger
    wiredTiger:
        engineConfig:
            cacheSizeGB: 0.5
            directoryForIndexes: false
        indexConfig:
            prefixCompression: true

systemLog:
    destination: file
    logAppend: true
    path: /var/log/mongodb/mongod.log
    verbosity: 1

net:
    port: 27017
    bindIp: 127.0.0.1
    maxIncomingConnections: 50

processManagement:
    fork: false
    timeZoneInfo: /usr/share/zoneinfo

replication:
    replSetName: replica

operationProfiling:
    slowOpThresholdMs: 2000
    mode: slowOp
```

:::warning
MongoDB transactions require replica sets to function, even for a standalone deployment.
:::

## Problem Analysis

I was able to see the timeout error when I tried to connect to the MongoDB server from the application:

```plaintext
MongoServerSelectionError: Server selection timed out after 30000 ms
```

However, I wasn't sure what's the cause because the MongoDB server log didn't show any further errors. What confused me more was that the MongoDB server behaved differently on different platforms:

- **ARM64 macOS**: Version mismatch warning appeared, and mongoDB connection failed
- **AMD64 Linux**: No issues, everything worked
- **ARM64 Purpose-Built Linux Board**: No warnings, but mongoDB connection failed

## Root Cause Analysis

After all the enabling and disabling of MongoDB features and application behaviors, I finally found the root cause was the mismatch configuration for replica sets. `storage.journal.enabled` was set to `false`, which is not compatible with replica sets with the WiredTiger storage engine,and it is actually stated in the [MongoDB documentation](https://www.mongodb.com/docs/v4.4/reference/configuration-options/#mongodb-setting-storage.journal.enabled):

:::primary
Starting in MongoDB 4.0, you cannot specify `--nojournal` option or `storage.journal.enabled: false` for replica set members that use the WiredTiger storage engine.
:::

### Debugging Challenges

The issue was simple, but it took me a long time to identify it due to several challenges:

- **Slow Build Times**: Time-consuming to test configuration changes. I had to wait for the Docker image to rebuild and redeploy each time. It took even longer on the purpose-built ARM64 board
- **Limited Debugging**: Performance issues that were happing in the same time. My Next.js application wasn't able to execute server actions, which were mainly for database operations, often experiencing lost connections with no reasons. In the meantime, the `cog` process was consuming a lot of CPU and crashed frequently

Obviously I should have read the documentation. But trying to fix multiple issues at the same time made it hard to focus on the root cause.

#### Management Script

The MongoDB server was run and managed with the following scripts:

```bash
wait_for_mongodb() {
    while true; do
        _MONGO_OUTPUT=$(mongo --eval "db.adminCommand('ping')" 2>&1 || echo "connection_failed")

        if echo "$_MONGO_OUTPUT" | grep --quiet "connection_failed"; then
            echo "Waiting for MongoDB server to start..."
        elif echo "$_MONGO_OUTPUT" | grep --quiet "shell and server versions do not match"; then
            echo "Waiting for MongoDB server to start..."
        elif echo "$_MONGO_OUTPUT" | grep --quiet '"ok" : 1'; then
            break
        else
            echo "Waiting for MongoDB server to start..."
        fi

        sleep 1
    done
}

mongodb() {
    set -o errexit

    trap 'kill -TERM "$_PID"' TERM

    sudo mongod --config /etc/mongod.conf --replSet "replica" &
    _PID=$!

    echo "Start MongoDB server."

    wait_for_mongodb

    mongo --eval 'rs.initiate({_id: "replica", members: [{_id: 0, host: "127.0.0.1:27017"}]});' --quiet

    while ! mongo --eval "rs.status().ok" --quiet > /dev/null 2>&1; do
        echo "Waiting for MongoDB replica set to start..."
        sleep 1
    done

    wait "$_PID"

    exit $?

    return 0
}
```
