While developing an embedded system that required MongoDB transactions in a Docker container, I encountered a misleading version mismatch error message that stopped me from starting the MongoDB server with the replica set. The issue happened when I tried to tune the MongoDB server configuration to troubleshoot some performance issues, which was basically disabling as much as possible the MongoDB server features to see if it would help with the performance. The servers, on Linux AMD64, macOS ARM64, and purpose-built Linux ARM64 board, raised different error messages and result codes, which made me spent extra time on debugging.

- **Docker Engine**: [20.10.17](https://docs.docker.com/engine/release-notes/20.10/#201017)

MongoDB transactions require replica sets to function, even in single-node deployments. This is a fundamental requirement - you cannot enable transactions on a standalone MongoDB instance. For embedded applications requiring ACID transactions, initializing a replica set becomes a critical startup requirement.

### Docker Containerization Context

Due to software requirements, the entire system runs within a single Docker container, including:

- Multiple Python scripts communicating with firmware
- Python gRPC servers
- RabbitMQ server and client
- MongoDB database
- Next.js frontend
- Avahi client for network discovery
- All services monitored with Supervisord

This "everything in one container" approach creates unique challenges for service initialization and version management.

### ARM64 Compatibility Issues

The version conflict stems from MongoDB compatibility limitations on ARM64 architecture. According to [MongoDB community discussions](https://www.mongodb.com/community/forums/t/mongodb-and-the-pi-4-on-ubuntu-64-bit-aka-armv8-0-a-support/220635/4), MongoDB versions 6+ and 8+ don't work reliably on certain ARM64 boards. This forced a downgrade to MongoDB 4.4.15, but the base Docker image contained a pre-existing MongoDB 6.0.4 installation.

## Problem Analysis

### Error Manifestation

The primary symptom was a MongoDB server selection timeout followed by replica set initialization failures:

```bash
pymongo.errors.ServerSelectionTimeoutError: connection closed,connection closed,connection closed, Timeout: 30s, Topology Description: <TopologyDescription id: ..., topology_type: ReplicaSetNoPrimary, servers: [<ServerDescription ('127.0.0.1:27017',) server_type: Unknown, rtt: None, error=AutoReconnect('connection closed')>]>
```

### Platform-Specific Behavior

| Platform           | Behavior                         | Impact                               |
| ------------------ | -------------------------------- | ------------------------------------ |
| macOS ARM64        | Version mismatch warning appears | gRPC issues emerge after MongoDB fix |
| Linux AMD64        | No issues                        | Everything works including gRPC      |
| Custom Board ARM64 | No MongoDB issues                | Separate gRPC connection failures    |

## Root Cause Analysis

### The Core Issue

The problem was more subtle than initially thought. While only MongoDB 4.4.15 was installed, the system was connecting to a MongoDB 6.0.4 server that:

- **Wasn't started with replication enabled** - Missing `--replSet` parameter
- **Was running from a different source** - Pre-existing service in base Docker image
- **Created version mismatch** - 4.4.15 shell connecting to 6.0.4 server

### Detection Pattern

I discovered that the version mismatch warning was the key indicator:

**When connecting to wrong server (6.0.4):**

```bash
user@docker-desktop:~/source$ mongo --eval "db.adminCommand('ping')"
MongoDB shell version v4.4.15
connecting to: mongodb://127.0.0.1:27017/?compressors=disabled&gssapiServiceName=mongodb
Implicit session: session { "id" : UUID("abe4e62e-6415-414a-9756-420f2c3948ee") }
MongoDB server version: 6.0.4
WARNING: shell and server versions do not match
{ "ok" : 1 }
```

**Attempting replica set initialization fails:**

```bash
user@docker-desktop:~/source$ mongo --eval 'rs.initiate({_id: "replica", members: [{_id: 0, host: "127.0.0.1:27017"}]});'
MongoDB shell version v4.4.15
connecting to: mongodb://127.0.0.1:27017/?compressors=disabled&gssapiServiceName=mongodb
Implicit session: session { "id" : UUID("930704a4-0d5c-4c7f-aa78-e683ced37a3b") }
MongoDB server version: 6.0.4
WARNING: shell and server versions do not match
{
        "ok" : 0,
        "errmsg" : "This node was not started with replication enabled.",
        "code" : 76,
        "codeName" : "NoReplicationEnabled"
}
```

**When connecting to correct server (4.4.15):**

```bash
MongoDB shell version v4.4.15
connecting to: mongodb://127.0.0.1:27017/
MongoDB server version: 4.4.15
```

### Container Investigation

Debugging in the container revealed that only MongoDB 4.4.15 was installed, but a MongoDB 6.0.4 server was running without replication support. The key insight was that the version mismatch warning indicated connection to the wrong MongoDB service, and the "NoReplicationEnabled" error confirmed that this server couldn't support transactions.

## Solution Implementation

### Key Insight

The version mismatch warning only appears when connecting to the wrong MongoDB server. When our correct MongoDB server (4.4.15) with replication enabled is running, there's no version mismatch warning and replica set operations succeed.

### Detection Logic

I used this pattern to detect when the correct MongoDB server is ready:

```bash
wait_for_mongodb() {
    while true; do
        _MONGO_OUTPUT=$(mongo --eval "db.adminCommand('ping')" 2>&1 || echo "connection_failed")

        if echo "$_MONGO_OUTPUT" | grep --quiet "connection_failed"; then
            helper_log "Waiting for MongoDB server to start..."
        elif echo "$_MONGO_OUTPUT" | grep --quiet "shell and server versions do not match"; then
            helper_log "Waiting for MongoDB server to start..."
        elif echo "$_MONGO_OUTPUT" | grep --quiet '"ok" : 1'; then
            break
        else
            helper_log "Waiting for MongoDB server to start..."
        fi

        sleep 1
    done
}
```

### Final Solution

The complete solution for MongoDB initialization with replica set setup:

```bash
# Wait for correct MongoDB version to be ready
wait_for_mongodb

# Check if replica set is already initialized
_REPLICAS_STATUS=$(mongo --eval "rs.status().ok" --quiet 2>/dev/null || echo "0")
if [ "$_REPLICAS_STATUS" != "1" ]; then
    helper_log "Initializing MongoDB replica set..."
    mongo --eval 'rs.initiate({_id: "replica", members: [{_id: 0, host: "127.0.0.1:'$PORT_MONGODB'"}]});' --quiet
else
    helper_log "MongoDB replica set already initialized."
fi

# Wait for replica set to be fully ready
while ! mongo --eval "rs.status().ok" --quiet > /dev/null 2>&1; do
    helper_log "Waiting for MongoDB replica set to start..."
    sleep 1
done
```

## Why This Solution Works

### State Detection Logic

| Condition                                | MongoDB State                                      | Action       |
| ---------------------------------------- | -------------------------------------------------- | ------------ |
| `connection_failed`                      | No MongoDB running                                 | Keep waiting |
| `shell and server versions do not match` | Wrong MongoDB (6.0.4, no replication) running      | Keep waiting |
| `"ok" : 1` AND no version warning        | Correct MongoDB (4.4.15, with replication) running | Proceed      |

### Benefits

- **Reliable Detection** - Uses version mismatch as definitive indicator
- **Platform Agnostic** - Works regardless of underlying system architecture
- **Self-Healing** - Automatically waits for correct server to start
- **Simple Logic** - Easy to understand and maintain

## Debugging Challenges

### Performance Constraints

The custom ARM64 board presented additional challenges:

- **Low Performance** - Unable to run development mode efficiently
- **Limited Debugging** - Difficult to get detailed debug messages
- **Slow Build Times** - Time-consuming to test configuration changes
- **Separate gRPC Issues** - Different connection problems masked the MongoDB issue

### Multi-Platform Complexity

Each platform exhibited different behavior patterns:

- **macOS ARM64** - Revealed the core MongoDB version issue clearly
- **Linux AMD64** - Masked the problem by working correctly out of the box
- **Custom ARM64** - Had separate gRPC issues that complicated diagnosis
