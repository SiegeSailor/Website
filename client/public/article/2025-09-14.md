While I was solving issues on [Next.js Server Action](/blog/2025-08-01) and [MongoDB Misleading Message](/blog/2025-06-26), I noticed that the WebKit `cog` rendering engine was crashing and flickering regularly on my purpose-built ARM64 board, which was not present on AMD64 Linux and ARM64 macOS, hence I tried to solve it by tuning Next.js and MongoDB setups. However, after resolving the issues mentioned above, I realized that the WebKit issues were still there and needed further investigation.

<!-- description -->

The two issues happening constantly and regularly:

- **Flickering**: Specific components flickered a lot. While users could still interact with the page, it was very distracting and made the app feel unstable. It mostly happened when a component either having multiple sub-components, updating relatively frequently (for example, a timer that updates once per second), or on top of 2 or more overlays
- **Crashing**: The WebKit process crashed regularly when navigating pages or making requests. The request, interesting, fired without request body. The console would output the message `⨯ [Error: The router state header was sent but could not be parsed.]` then restart the browser

## Attempts

There were some flags I used to launch `cog` to help with mitigating the issues. Although I did not find they worked, I kept them in my launch script as it did not hurt the performance or stability:

- `--web-mem-limit`
- `--network-mem-limit`
- `--no-page-cache`
- `--disable-web-security`

The flickering issue persisted, I then thought it might be related to hardware acceleration, especially GPU acceleration. I tried enabling them one by one:

- `--enable-2d-canvas-acceleration`
- `--enable-web-gl`

Unfortunately, they both raised the `g_object_unref: assertion 'G_IS_OBJECT (object)' failed` error and stopped `cog` from launching, so I had to remove them. I them tried to mount GPU devices into the Docker container and installed necessary drivers, but the flickering issue still persisted:

```shell
docker run \
    ... \
	--device=/dev/galcore \
	--device=/dev/dri/card0 \
	--device=/dev/dri/card1 \
	--device=/dev/dri/renderD128 \
	--volume /usr/lib/libEGL.so:/usr/lib/libEGL.so:ro \
	--volume /usr/lib/libEGL.so.1:/usr/lib/libEGL.so.1:ro \
	--volume /usr/lib/libGLESv2.so:/usr/lib/libGLESv2.so:ro \
	--volume /usr/lib/libGLESv2.so.2:/usr/lib/libGLESv2.so.2:ro \
	--volume /usr/lib/libGLSLC.so:/usr/lib/libGLSLC.so:ro \
	...
```

## Solution to Crashing

This idea was out of nowhere. While I was thinking about the `⨯ [Error: The router state header was sent but could not be parsed.]` issue, I thought about not increasing the memory limit but disabling them completely because the crashing behavior looked like a memory corruption issue, meaning that the browser tried to release and load new chunk of data but it failed every time trying to do so, leading to a crash:

```javascript title="./next.config.mjs"
const nextConfig = {
  cacheMaxMemorySize: 0,
  reactMaxHeadersLength: 1000,
  experimental: {
    serverActions: { bodySizeLimit: "1mb" },
  },
  headers: async () => [
    // remove this header
    { source: "/:path*", headers: [{ key: "x-next-router-state-size", value: "100000" }] },
  ]
  ...
}
```

And, in the entry `layout.ts`, I forced Next.js to always render the page dynamically without caching any data:

```typescript title="./src/app/layout.ts"
export const dynamic = "force-dynamic";
export const fetchCache = "force-no-store";
export const revalidate = 0;
export const runtime = "nodejs";
```

Surprisingly, this solved the crashing issue completely. What was more surprising was that this also solved [Next.js Server Action](/blog/2025-08-01). After running the app for multiple hours and navigating through different pages, the WebKit process did not crash once.
