I encountered a challenge while deploying multiple GitLab Pages with the `environment` keyword using Git tags generated by Semantic Release. These tags, such as `1.1.2`, are created dynamically at runtime after commit analysis, making them unavailable during the initial pipeline configuration. As a result, the GitLab CI/CD pipeline failed to parse the YAML file due to empty fields like `url: $NEXT_VERSION`:

```mermaid
graph LR
  BT(Build Time) --> P[Provision CI/CD YAML]
  P --> |pipeline fails| RT(Runtime)
```

After some trial and error, I discovered [GitLab Docs Dynamic Pipelines](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/#dynamic-child-pipelines) as a solution. However, implementing them required overcoming several undocumented issues.

:::note
The GitLab version used in this article is GitLab Enterprise Edition `18.5.0-pre 04836b117ff`.
:::

### Pipeline Goals

The pipeline aims to achieve the following:

- Automatically create Git tags based on commit messages
  - Git tag is only known during the pipeline, so the pipeline is not triggered by Git tag creation
- Deploy the same build to different GitLab Pages
  - Access the deployed sites using URLs like:
    - `/`: For the latest commit across all branches
    - `/x.x.x(-<branch_name>.#)?`: For the published releases. The optional suffix is for pre-releases
    - `<branch_name>`: For the latest commit in a branch

## Setting Up YAML

See the comments for details. Some configurations are omitted for brevity. First of all, define the workflow rules and stages:

```yml title="./.gitlab-ci.yml"
workflow:
  rules:
    - if: "$CI_PIPELINE_SOURCE == 'merge_request_event'"
    # list branches that need to deploy to GitLab Pages
    - if: "$CI_COMMIT_BRANCH == 'main'"
    - if: "$CI_COMMIT_BRANCH == 'release'"

stages:
  - "build"
  - "release"
  - "deploy"
  # create YAML for dynamic pipeline
  - "prepare"
  # trigger dynamic pipelines
  - "trigger"

default:
  image: "node:22.18"
```

### Build Stage

Then, define the job that builds the project. We serve the same build to different GitLab Pages, so we only need to build once. Note that we save the job ID `.build-job-id` and the compressed build `build.zip` for dynamic pipeline to fetch artifacts, and `build/` is the directory that contains the build output for the deploy jobs that defined in the same pipeline:

```yml title="./.gitlab-ci.yml"
build-project:
  stage: "build"
  before_script: |
    apt-get update
    apt-get install --yes zip
  script: |
    npm run "ci:${CI_JOB_NAME}"
    echo $CI_JOB_ID > "./.build-job-id"
    zip -r "build.zip" "./build/"
  artifacts:
    paths:
      - "./build/"
      - "./.build-job-id"
      - "./build.zip"
    expose_as: "Project Build"
```

:::fact
Replace or implement the project build script for `npm run "ci:${CI_JOB_NAME}"`.
:::

### Release Stage

The file `.next-release-version` is created by Semantic Release to store the one-line text, the generated Git tag, for the dynamic pipeline to read:

```yml title="./.gitlab-ci.yml"
publish-registry-release:
  rules:
    # list branches that need to deploy to GitLab Pages
    - if: "$CI_COMMIT_BRANCH == 'main'"
    - if: "$CI_COMMIT_BRANCH == 'release'"
  stage: "release"
  variables:
    GITLAB_TOKEN: $PROJECT_ACCESS_TOKEN
    NODE_ENV: "production"
    NPM_TOKEN: $PROJECT_ACCESS_TOKEN
  before_script: |
    ...
  script: |
    npm config set "//${CI_SERVER_HOST}/api/v4/packages/npm/:_authToken" $PROJECT_ACCESS_TOKEN --location "project"
    npm config set "//${CI_SERVER_HOST}/api/v4/projects/${CI_PROJECT_ID}/packages/npm/:_authToken" $PROJECT_ACCESS_TOKEN --location "project"
    npm run "ci:${CI_JOB_NAME}"
  artifacts:
    paths:
      - "./.next-release-version"
    expose_as: "Release Information"
    expire_in: "1 day"
  dependencies:
    - "build-project"
```

:::fact
Replace or implement the project release script for `npm run "ci:${CI_JOB_NAME}"`. It should at least run `NODE_ENV=production semantic-release` internally.
:::

:::fact
The `.next-release-version` is generated by [Semantic Release Exec](https://www.npmjs.com/package/@semantic-release/exec) during the `prepare` step. See the following snippet for Semantic Release plugins configuration:

```js title="./release.config.mjs"
export default {
  branches: [ ... ],
  plugins: [
    "@semantic-release/commit-analyzer",
    "@semantic-release/release-notes-generator",
    [
      "@semantic-release/npm",
      { npmPublish: true, ... },
    ],
    [
      "@semantic-release/gitlab",
      {
        assets: [{ ... }],
        gitlabApiPathPrefix: "/api/v4",
        gitlabUrl: "https://gitlab.com",
      },
    ],
    [
      "@semantic-release/exec",
      { prepareCmd: "echo ${nextRelease.version} > ./.next-release-version" },
    ],
  ],
  tagFormat: "${version}",
};
```

:::

:::note
The `before_script` configures the project access for Semantic Release to push the Git tag back to the repository. You are free to skip it if you have already set up the Git access in other ways:

```shell
mkdir -p ~/.ssh
chmod 700 ~/.ssh
chmod 600 $PROJECT_SSH_KEY_GIT
eval $(ssh-agent -s)
ssh-add $PROJECT_SSH_KEY_GIT
ssh-keyscan $CI_SERVER_HOST >> ~/.ssh/known_hosts
chmod 644 ~/.ssh/known_hosts
git remote set-url origin "git@${CI_SERVER_HOST}:${CI_PROJECT_PATH}.git"
```

For `$PROJECT_SSH_KEY_GIT`, You will have to generate a SSH key pair and configure the public key in [GitLab Docs Deploy Keys](https://docs.gitlab.com/user/project/deploy_keys/) and the private key in CI/CD variables named as `$PROJECT_SSH_KEY_GIT` in [GitLab Docs CI/CD Variables](https://docs.gitlab.com/ci/variables/). You can generate the SSH key pair using the following command:

```shell
ssh-keygen -t ed25519 -C "semantic-release-bot" -f "./.ssh/gitlab-ci-bot"
```

The `$PROJECT_ACCESS_TOKEN` (`$GITLAB_TOKEN` and `$NPM_TOKEN`, required by [Semantic Release GitLab](https://www.npmjs.com/package/@semantic-release/gitlab)) variable is a Deploy Token, also needed to be configured in CI/CD variables. You can skip this if you don't see the error message _remote: Git access over HTTP is not allowed_ in the job log.
:::

### Deploy Stage

We then create the jobs for deploying pages to `/` and `<branch_name>` following [Pipeline Goals](#pipeline-goals):

```yml title="./.gitlab-ci.yml"
.deploy-pages: &deploy-pages
  stage: "deploy"
  tags:
    - $RUNNER
  script: |
    echo "Deployed to $CI_PAGES_URL"
  dependencies:
    - "build-ladle"

deploy-pages-latest:
  <<: *deploy-pages
  pages:
    publish: "./build/"
    expire_in: "never"
  environment:
    name: "Pages"
    url: $CI_PAGES_URL

deploy-pages-reference:
  <<: *deploy-pages
  pages:
    publish: "./build/"
    path_prefix: $CI_COMMIT_REF_NAME
    expire_in: "1 months"
  environment:
    name: "Pages ${CI_COMMIT_REF_NAME}"
    url: $CI_PAGES_URL
```

:::note
`$CI_PAGES_URL` is the predefined variable for GitLab Pages URL. It is generated based on the project namespace, name, and `pages:path_prefix`.
:::

### Prepare Stage

This job creates the dynamic pipeline YAML file `.gitlab-ci.deploy-pages-release.yml` using the artifacts `.build-ladle-job-id` and `.next-release-version` from previous jobs. It only runs when the file `.next-release-version` exists, indicating that a new release has been published:

```yml title="./.gitlab-ci.yml"
create-deploy-pages-release:
  rules:
    - exists:
        - "./.next-release-version"
  stage: "prepare"
  tags:
    - $RUNNER
  script: |
    BUILD_LADLE_JOB_ID=$(cat ./.build-ladle-job-id) FILENAME=".gitlab-ci.deploy-pages-release.yml" NEXT_RELEASE_VERSION=$(cat ./.next-release-version) \
      npm run "ci:${CI_JOB_NAME}"
  artifacts:
    paths:
      - "./.gitlab-ci.deploy-pages-release.yml"
    expose_as: "Dynamic Pipeline Configuration"
    expire_in: "1 day"
  dependencies:
    - "build-ladle"
    - "publish-registry-release"
```

:::fact
Replace or implement the project deploy script for `npm run "ci:${CI_JOB_NAME}"`. It should at least generate the dynamic pipeline YAML file `.gitlab-ci.deploy-pages-release.yml`. [Jsonnet](https://github.com/google/jsonnet) is one of the most recommended tools, but you can use any language to implement it as long as you can parse, substitute, and write YAML files. For details about downloading artifacts using `curl`, see [Artifact Size Limit](#artifact-size-limit):

```javascript
import { writeFileSync } from "fs";

const { BUILD_LADLE_JOB_ID, FILENAME, NEXT_RELEASE_VERSION } = process.env;

const template = `
deploy-pages-release:
  stage: "deploy"
  script: |
    curl --location --output "./download.zip" --header "PRIVATE-TOKEN: $PROJECT_ACCESS_TOKEN" --url "https://$CI_SERVER_HOST/api/v4/projects/$CI_PROJECT_ID/jobs/${BUILD_LADLE_JOB_ID}/artifacts/build.zip"
    unzip "./download.zip"
    echo "Deployed to $CI_PAGES_URL"
  pages:
    publish: "./build/"
    path_prefix: ${NEXT_RELEASE_VERSION}
    expire_in: "never"
  environment:
    name: "Pages ${NEXT_RELEASE_VERSION}"
    url: $CI_PAGES_URL
`;

writeFileSync(`./${FILENAME}`, template);
```

:::

### Trigger Stage

This job triggers the pipeline `./.gitlab-ci.deploy-pages-release.yml` created previously. The keyword `trigger` is used specifically for this matter:

```yml title="./.gitlab-ci.yml"
trigger-deploy-pages-release:
  rules:
    - exists:
        - "./.gitlab-ci.deploy-pages-release.yml"
  stage: "trigger"
  trigger:
    include:
      - artifact: ".gitlab-ci.deploy-pages-release.yml"
        job: "create-deploy-pages-release"
    strategy: "mirror"
  needs:
    - job: "create-deploy-pages-release"
      artifacts: true
```

## Challenges and Solutions

I've read through the following documents before implementing dynamic pipelines:

- [GitLab Docs CI/CD YAML Syntax Reference](https://docs.gitlab.com/ci/yaml/#triggerinclude)
- [GitLab Docs Dynamic Pipelines](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/#dynamic-child-pipelines)
- [GitLab Forum Using User Defined Environment Variables with Dynamic Environments](https://forum.gitlab.com/t/using-user-defined-environment-variables-with-dynamic-environments-or-multi-project-pipelines/54258/4)
- [Medium Stop Running Static Jobs in GitLab, Run Dynamically Created Jbs Instead](https://medium.com/@datails/stop-running-static-scoped-jobs-in-gitlab-run-dynamically-created-jobs-instead-481bb686cea5)

However, they don't cover all the errors I encountered.

### Dependency

Something tricky about dependencies between jobs in the main pipeline and the dynamic pipeline as they don't always appear and are in different scopes. If a job is depended by another job using `needs`, it must exist. Otherwise, the job that depends on the other fails automatically. In our [Prepare Stage](#prepare-stage), `create-deploy-pages-release` only exists when `./.next-release-version` exists. So I had to add `rules:exists: ./.gitlab-ci.dynamic.yml` to prevent the job from failing.

The other option is to add `needs:optional: true` to always allow the job to run even if the depended job doesn't exist. However, it may lead to unexpected behaviors if the job really needs the depended job to run correctly.

### Isolated Pipelines

This is probably the nature of _Dynamic_. Dynamic child pipelines don't share anything from main pipeline, including dependencies, stage, variable, default, etc, meaning that using aliases `*` to reference anchors in the parent pipeline `gitlab-ci.yml` is not supported. So you have to repeat the configuration if needed.

### CI Token Limitation

Authenticating with `$CI_JOB_TOKEN` from the dynamic child pipeline to its parent doesn't work. I had to use `$PROJECT_ACCESS_TOKEN`. See [Release Stage](#release-stage) for more details about generating the token.

### Artifact Size Limit

There is a `5mb` size limit for the artifact passed by [Trigger Stage](#trigger-stage) using the `trigger:include:artifact` keyword to the dynamic pipeline. To work around this, I downloaded the build artifact to the dynamic pipeline job using [GitLab Docs Job Artifacts API](https://docs.gitlab.com/api/job_artifacts/#download-a-single-artifact-file-by-job-id).
