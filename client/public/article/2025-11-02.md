While experimenting with Python Semantic Release in GitHub Actions in [Smarty-Notebook](https://github.com/SiegeSailor/Smarty-Notebook), I encountered several issues and have noticed the difference between the one in the NPM ecosystem. I am here to document my findings and my settings for future reference.

:::note
The GitHub version used in this article is GitHub Non-Enterprise Edition to the date _2025-11-02_.
:::

<!-- description -->

### Pipeline Goals

The pipeline aims to achieve the following:

- Automatically create Git tags and GitHub releases, and update Changelog based on commit messages
- Bundle a serial of files as assets for each release

:::note
There is no build, test, package, and publish steps in this pipeline, as [Smarty-Notebook](https://github.com/SiegeSailor/Smarty-Notebook) only contains Jupyter Notebooks. See [Smarty-Notebook Contributing Branching Strategy](https://github.com/SiegeSailor/Smarty-Notebook?tab=contributing-ov-file#branching-strategy) for more details.
:::

## Setting Up YAML

See the comments for details. Some configurations are omitted for brevity. First of all, define the triggers and default permissions:

```yml title="./.github/workflows/continuous-delivery.yml"
name: Continuous Delivery

on:
  push:
    branches: [main, release]
  pull_request:
    branches: [main, release]
    types: [edited, opened, reopened, synchronize]

permissions:
  contents: read
```

:::note
You may want to adjust the `on` rules if you don't want to trigger two pipelines for both `push` and `pull_request` events when pushing changes to a branch that is having active pull requests.
:::

### Linting Job

Define a job for linting the commit messages using [Commitlint Action](https://github.com/opensource-nepal/commitlint). This will ensure all commit messages live in the PR comply with the conventional commit format:

```yml title="./.github/workflows/continuous-delivery.yml"
jobs:
  linting:
    runs-on: ubuntu-latest

    permissions:
      contents: read
      pull-requests: read

    steps:
      - name: Action | Validate Commit Messages
        uses: opensource-nepal/commitlint@v1.3.1
```

#### Validate PR Title

Add the following steps to `steps` to validate PR titles. `commitlint` does not support validating PR titles out of the box. However, we can set up a custom step to validate the PR title using the same `commitlint` package. Here is an example of how to do it. First, we need to check out the repository at the PR head SHA:

```yml title="./.github/workflows/continuous-delivery.yml"
steps:
  ...

  - name: Action | Checkout Repository on Pull Request
    uses: actions/checkout@v5.0.0
    if: github.event_name == 'pull_request'
    with:
      # we only need to initialize the Git directory
      fetch-depth: 1
      ref: ${{ github.event.pull_request.head.sha }}
      token: ${{ secrets.GITHUB_TOKEN }}

  - name: Action | Set Up Python
    uses: actions/setup-python@v6.0.0
    if: github.event_name == 'pull_request'
    with:
      python-version: 3.11.13

  - name: Setup | Install Commitlint
    if: github.event_name == 'pull_request'
    run: pip install commitlint

  - name: Evaluate | Validate PR Title
    if: github.event_name == 'pull_request'
    run: commitlint "${{ github.event.pull_request.title }}"
```

| With `pull_request` Event                                               | With `push` Event                                                             |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| ![With-Validate-PR-Title](/image/2025-11-02/With-Validate-PR-Title.png) | ![Without-Validate-PR-Title](/image/2025-11-02/Without-Validate-PR-Title.png) |

:::fact
I opened [GitHub Commitlint Issues#79 PR Title or Custom Commit Validation on GitHub Action](https://github.com/opensource-nepal/commitlint/issues/79) regarding the PR title validation feature. By the way, trying to commit the PR title to pass them to `commitlint` during the pipeline run will not work. It seems that `commitlint` does not read local commits on the runner. See [Smarty Notebook GitHub Action Linting Job](https://github.com/SiegeSailor/Smarty-Notebook/actions/runs/19212728519/job/54917412427).
:::

:::fact
`commitlint` fetches the whole PR commit history when triggered by `pull_request`, and only fetches the latest commit when triggered by `push`.
:::

### Release Job

This is a modified version of [Python Semantic Release GitHub Action Common Workflow Example](https://python-semantic-release.readthedocs.io/en/latest/configuration/automatic-releases/github-actions.html#common-workflow-example). Some steps are simplified with `...`, as they are not changed from the workflow example. The key change is including the GitHub App to bypass repository settings for branch rulesets and other contribution constraints. You can remove the **Action | Create GitHub App Token** step and replace `${{ steps.action-create-github-app-token.outputs.token }}` with `${{ secrets.GITHUB_TOKEN }}` if you haven't defined anything special in your repository settings:

```yml title="./.github/workflows/continuous-delivery.yml"
release:
  runs-on: ubuntu-latest
  needs: linting
  concurrency:
    group: ${{ github.workflow }}-${{ github.job }}-${{ github.ref_name }}
    cancel-in-progress: false

  permissions:
    # we need write access to create tags and releases
    contents: write
    pull-requests: write

  steps:
    - name: Action | Create GitHub App Token
      uses: actions/create-github-app-token@v2.1.4
      id: action-create-github-app-token
      with:
        app-id: ${{ vars.APP_ID_GITHUB_APP_BYPASS_RULESETS }}
        private-key: ${{ secrets.PRIVATE_KEY_GITHUB_APP_BYPASS_RULESETS }}

    - name: Action | Checkout Repository on Release Branch
      uses: actions/checkout@v5.0.0
      with:
        fetch-depth: 0
        ref: ${{ github.ref_name }}
        token: ${{ steps.action-create-github-app-token.outputs.token }}

    - name: Setup | Force Release Branch to be at Workflow SHA
      run: ...

    - name: Evaluate | Verify Upstream has NOT Changed
      shell: bash
      run: ...
```

We can now be sure that the commit living here is the newest one and is not interfered by other pushes, and the token has sufficient permissions to create releases and tags even with branch rule sets enabled. We can now continue to go through the core steps:

```yml title="./.github/workflows/continuous-delivery.yml"
steps:
  ...

  - name: Build | Compress Artifacts
      run: zip -r notebooks.zip ./notebooks/

  - name: Action | Create Semantic Version Release
    id: python-semantic-release-release
    uses: python-semantic-release/python-semantic-release@v10.4.1
    with:
      github_token: ${{ steps.action-create-github-app-token.outputs.token }}
      git_committer_name: "github-actions"
      git_committer_email: "actions@users.noreply.github.com"
      config_file: "./releaserc.toml"
      verbosity: 1

  - name: Action | Publish to GitHub Release Assets
    uses: python-semantic-release/publish-action@v10.4.1
    if: steps.python-semantic-release-release.outputs.released == 'true'
    with:
      github_token: ${{ steps.action-create-github-app-token.outputs.token }}
      tag: ${{ steps.python-semantic-release-release.outputs.tag }}

  - name: Action | Upload Artifacts
    uses: actions/upload-artifact@v5.0.0
    with:
      name: notebooks
      path: "./notebooks/"
      if-no-files-found: error

outputs:
  released: ${{ steps.python-semantic-release-release.outputs.released || 'false' }}
```

:::fact
Replace or implement the artifacts build and upload details for **Build | Compress Artifacts** and **Action | Upload Artifacts**. See [Publish Assets](#publish-assets) about the assets publishing details.
:::

#### GitHub Project Settings and App Permission

Skip the following if you didn't configure any branch rule sets or contribution constraints in your repository settings. Some of the rules here will block the our GitHub Action from creating releases and tags:

![Branch-Rules](/image/2025-11-02/Branch-Rules.png)

##### Create a GitHub App

To bypass these rules, we will need to create a GitHub App with sufficient permissions. We will have to go to the Developer Settings page on our Personal Settings page. You can create an App with border permissions that can only be installed on your repositories, or create an App with narrow permissions that can be installed on any repositories:

![GitHub-Apps](/image/2025-11-02/GitHub-Apps.png)

You will need to take a note of your **App ID**:

![GitHub-App-About](/image/2025-11-02/GitHub-App-About.png)

And you will have to create a **Private Key** for later use in the GitHub Action:

![GitHub-App-Private-Key](/image/2025-11-02/GitHub-App-Private-Key.png)

##### Configure the GitHub App

Add the **App ID** and **Private Key** to your GitHub Action secrets and variables:

![Settings-Actions-Secret](/image/2025-11-02/Settings-Actions-Secret.png)

After that, install the GitHub App to your repository:

![Settings-GitHub-Apps](/image/2025-11-02/Settings-GitHub-Apps.png)

Finally, add the installed GitHub App to the bypass list:

![Settings-Branch-Bypass](/image/2025-11-02/Settings-Branch-Bypass.png)

:::fact
You must use the same token for all the following steps in the same job.
:::

:::note
Although using a GitHub App to bypass branch rule sets is recommended, you can also use a Personal Access Token with sufficient permissions. You can do so by replacing `${{ steps.action-create-github-app-token.outputs.token }}` with `${{ secrets.PAT }}`. You will need to configure your `${{ secrets.PAT }}` in the GitHub Action Secret page. However, using a PAT will make it harder for traceability and have to be rotated every time the user is removed from the repository.
:::

:::note
As of _2025-11-02_, Deploy Keys are not able to bypass branch rule sets. See [Challenges and Solutions](#challenges-and-solutions).
:::

#### Publish Assets

It is worth to mention that **Action | Create Semantic Version Release** runs before **Action | Publish to GitHub Release Assets**. Unlike GitLab, the assets are not automatically attached to each release created. We publish assets after the release is created. This actually disallow us to **Enable release immutability**. We will have to disable it:

![Settings-General](/image/2025-11-02/Settings-General.png)

:::note
There might be a way to temporarily enable and disable the release immutability using GitHub API, but it will introduce a repository-level concurrency issue.
:::

In `./releaserc.toml`, we configure the assets to be published:

```toml title="./releaserc.toml"
[semantic_release]
assets = ["./README.md", "./notebooks.zip"]
```

##### Artifacts and Assets

This might not be too strange to someone who has experience with GitHub Actions and GitHub Releases, but I found it quite confusing that the assets uploaded using `python-semantic-release/publish-action@v10.4.1` are not the same as the artifacts uploaded using `actions/upload-artifact@v5.0.0`. The former are attached to each GitHub Release, while the latter are stored in the workflow run page:

Here are some additional notes.

### Prerelease Token

Unlike the NPM version, where we can use the branch name as a variable in `channel`, so-called `prerelease_token` in the Python version, string:

```javascript
{
  branches: [
    "main",
    { name: "release", prerelease: true, channel: "${name}" },
    { name: "hotfix-*", prerelease: true, channel: "${name}" },
  ],
}
```

The Python version requires us to pass the `prerelease_token` using the `--build-metadata` flag.

### Poetry Compatibility

`poetry` verifies the `project.version` field in the `pyproject.toml` file. However, PSR updates the version according to the latest published release, which can be a prerelease version that is not compatible with `poetry`'s version scheme. Therefore, we have to disable the `version_toml` plugin:

```toml title="./releaserc.toml"
[semantic_release]
version_toml = []
```

### Commit Message Template

The default `commit_message` template in PSR does not comply with the conventional commit format. Therefore, we have to override it:

```toml title="./releaserc.toml"
[semantic_release]
commit_message = """\
chore: release {version}

Automatically generated by python-semantic-release
"""
```
