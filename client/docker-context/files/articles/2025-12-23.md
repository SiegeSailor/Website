This is for this website, [Jin Yu Zhang's Website](https://jinyu-zhang.com). I deployed my previous version using AWS Amplify, which was relatively easy to use, but I wanted to have more control over the infrastructure and get some hands-on experience with AWS and Terraform. So I decided to migrate from AWS Amplify to ECS Fargate using Terraform all through IaC practices.

<!-- description -->

First thing comes first, I checked my AWS billing dashboard and it was only around $2.50 USD per month:

![AWS-Console-Billing-November](/images/2025-12-23/AWS-Console-Billing-November.png)

The first month after migrating to ECS Fargate, my bill was around $38.00 USD. I knew I have been spending much more than I needed, especially on VPC Endpoint Hour and NAT Gateway Hour:

![AWS-Console-Billing-December](/images/2025-12-23/AWS-Console-Billing-December.png)

### Project Structure

Just for context, my website is a Next.js application containerized using Docker. The Docker image is pushed to AWS Elastic Container Registry (ECR) and deployed using AWS ECS Fargate behind an Application Load Balancer (ALB), which utilizes VPC private subnets and route53 for DNS management. My website is a monorepo and it ends up like below:

```plaintext
└── 📁 [module]
    └── 📁 docker-context
    └── 📁 infrastructure
        └── 📁 [environment]
    └── 📁 scripts
└── 📁 shared-infrastructure
    └── 📁 [environment]
└── 📁 scripts
├── .gitignore
├── CONTRIBUTING.md
└── README.md
```

Ideally, I should be able to share network configurations across multiple modules, such as resources like VPC, subnets, and security groups. Therefore, I created a `shared-infrastructure` folder at the root level to hold shared resources. Each environment, such as `production` and `development`, has its own folder within `shared-infrastructure` and `infrastructure` to manage environment-specific configurations.

### Challenges

Issues discovered after migrating from AWS Amplify to ECS Fargate using Terraform.

#### AWS Certificate Manager for CloudFront Distribution

It took me a while to realize that there was a requirement for ACM to be in `us-east-1` when using CloudFront Distribution. It was actually documented in [AWS Requirements for Using SSL/TLS Certificates with CloudFront](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cnames-and-https-requirements.html). Initially, I had all my resources in `us-west-2`, including ACM, and couldn't figure out why I couldn't access my website, until I realized this requirement. I then decided to destroy all my resources and recreate them in `us-east-1`. The migration took me a while as I as moved my Terraform backend from S3 in `us-west-2` to S3 in `us-east-1` as well. I though I had to manually delete some resources as they were dependent on each other, such as security groups attached to load balancers, but I found some flags like `enable_deletion_protection` to apply before running `terraform destroy`.

#### Health Check Failing due to Missing Environment Variables

My client module, which is a Next.js application, had a Dockerfile that defined some environment variables:

```docker title="./client/docker-context/Dockerfile"
ENV HOSTNAME="0.0.0.0"
ENV NODE_ENV="production"
ENV PORT="3000"
```

Which should be enough for accessing the Next.js application on port 3000. I then had a health check command defined in my ECS task definition like below:

```terraform
healthCheck = {
  command     = ["CMD-SHELL", "curl -f http://127.0.0.1:${local.port} || exit 1"]
  interval    = 30
  timeout     = 5
  retries     = 3
  startPeriod = 60
}
```

And another health check defined in my Application Load Balancer target group like below:

```terraform
target_groups = {
  (local.module) = {
    name_prefix          = "alb-"
    protocol             = "HTTP"
    port                 = local.port
    target_type          = "ip"
    deregistration_delay = 30

    health_check = {
    enabled             = true
    interval            = 30
    path                = "/"
    port                = "traffic-port"
    healthy_threshold   = 2
    unhealthy_threshold = 5
    timeout             = 15
    protocol            = "HTTP"
    matcher             = "200-399"
  }

    create_attachment = false
  }
}
```

However, both health checks were constantly showing `Unknown` or `Unhealthy`, no matter what tool or path I used. I tried using `curl`, `wget`, and `ss` to check the port, and I also tried to implement a custom health check endpoint in my Next.js application, but nothing worked. Then I found out that defining environment variables in `Dockerfile` wasn't sufficient. Somehow ECS tasks washed out those environment variables at runtime. I had to define the variables in the ECS task definition to ensure they were accessible at runtime:

```terraform
container_definitions = {
  (local.module) = {
    environment = [
      {
        name  = "HOSTNAME"
        value = "0.0.0.0"
      },
      {
        name  = "NODE_ENV"
        value = "production"
      },
      {
        name  = "PORT"
        value = tostring(local.port)
      }
    ]
  }
}
```

#### Application Load Balancer Cache Undesired Next.js Dynamic Responses

I assumed that I could cache my Next.js pages at the ALB level, so I added the following cache behavior in my ALB listener rules:

```terraform
default_cache_behavior = {
  target_origin_id       = "alb"
  viewer_protocol_policy = "redirect-to-https"

  allowed_methods = ["GET", "HEAD", "OPTIONS"]
  cached_methods  = ["GET", "HEAD"]
  compress        = true
  query_string    = true

  # 30 days
  default_ttl = 2592000
  min_ttl     = 0
  # 1 year
  max_ttl = 31536000
}
```

Then all my pages, except for the `/` page, started to show plain text responses. The responses contained only Next.js headers and some information like time to live. I haven't figured out the exact reason, but I guess this happened because of [Next.js Streaming](https://nextjs.org/docs/app/getting-started/linking-and-navigating#streaming). I then removed the `*_ttl` fields from the default cache behavior from the ALB listener rules, and only cached images in the public folder since they are just static files. Everything worked again:

```terraform
ordered_cache_behavior = [{
  path_pattern           = "/images/*"
  target_origin_id       = "alb"
  viewer_protocol_policy = "redirect-to-https"

  allowed_methods = ["GET", "HEAD", "OPTIONS"]
  cached_methods  = ["GET", "HEAD"]
  compress        = true
  query_string    = true
  # 30 days
  default_ttl = 2592000
  min_ttl     = 0
  # 1 year
  max_ttl = 31536000
}]
```

#### Excessive Costs from VPC Endpoints and NAT Gateways

I discovered that after running the new architecture for 12 days that it is $0.045 per NAT Gateway Hour, which costs me around $13.00 USD. Amazingly high:

```terraform
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.5.1"

  name = "${local.project}-${local.environment}"
  cidr = "10.0.0.0/16"

  azs             = ["${var.aws_region}a", "${var.aws_region}b", "${var.aws_region}c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true

  tags = local.shared_tags
}
```

Then, I turned `enable_nat_gateway` to `false` and added the following VPC endpoints to reduce costs:

```terraform
resource "aws_vpc_endpoint" "ecr_api" {
  service_name        = "com.amazonaws.${var.aws_region}.ecr.api"
  vpc_endpoint_type   = "Interface"
  ...
}

resource "aws_vpc_endpoint" "ecr_dkr" {
  service_name        = "com.amazonaws.${var.aws_region}.ecr.dkr"
  vpc_endpoint_type   = "Interface"
  ...
}

resource "aws_vpc_endpoint" "s3" {
  service_name      = "com.amazonaws.${var.aws_region}.s3"
  vpc_endpoint_type = "Gateway"
  ...
}

resource "aws_vpc_endpoint" "logs" {
  service_name        = "com.amazonaws.${var.aws_region}.logs"
  vpc_endpoint_type   = "Interface"
  ...
}
```

However, it was $0.01 per VPC Endpoint Hour, and I had 3 endpoints excluding the S3 endpoint, which was of type Gateway and it was free. These costed me around $5.40 USD 5 days after adding VPC endpoints. The cost was almost the same using NAT Gateways. I came across [AWS Centralized Access to VPC Private Endpoints](https://docs.aws.amazon.com/whitepapers/latest/building-scalable-secure-multi-vpc-network-infrastructure/centralized-access-to-vpc-private-endpoints.html). This whitepaper suggests creating a centralized VPC to host shared resources like VPC endpoints and using VPC peering or AWS Transit Gateway to connect other VPCs to the centralized VPC. Then, I found out that I was already doing it. I has a shared VPC for all my modules and environments.

I needed to reduce the cost no matter what. I summarized some cost breakdowns that surprised me (excludes deployment on `us-east-2` since I only deployed there for less than a day):

| Service | Description                                                   | Usage Quantity | Amount (USD) |
| ------- | ------------------------------------------------------------- | -------------: | -----------: |
| ALB     | _$0.0225 per Application LoadBalancer-hour (or partial hour)_ |      192 Hours |        $4.32 |
| EC2     | _$0.045 per GB Data Processed by NAT Gateways_                |      80.178 GB |        $3.61 |
| EC2     | _$0.045 per NAT Gateway Hour_                                 |      297 Hours |       $13.37 |
| ECS     | _AWS Fargate - vCPU_                                          |  103.785 Hours |        $4.20 |
| VPC     | _$0.005 per In-use public IPv4 address per hour_              |  690.749 Hours |        $3.45 |
| VPC     | _$0.01 per VPC Endpoint Hour_                                 |      657 Hours |        $6.57 |

After analyzing the cost breakdown, I went for the following optimizations:

- **Service Connections (ECR and CloudWatch Logs)**: The VPC Interface Endpoints for ECR (`ecr.api` and `ecr.dkr`) and CloudWatch Logs (`logs`) were costing $0.01/hour each, totaling \~$22.00/month for the three endpoints. While NAT Gateway was even more expensive at $0.045/hour (~$32.00/month)
- **Public IPv4 Addresses**: The 690.749 hours of public IPv4 usage suggested multiple resources with public IPs
- **Fargate CPU/Memory**: My CPU and memory setup was overkill for a Next.js personal website

:::note
ALB costs were not optimized as it was my backbone to route traffic to ECS tasks, although it could cost me \~$17.00 per month.
:::

The first solution was to use the **free Internet Gateway** instead of expensive NAT Gateways or VPC Endpoints. I then removed all Interface-type `aws_vpc_endpoint` resources (keeping only the free S3 Gateway endpoint) and set `enable_nat_gateway` to `false` in my `vpc` module:

```terraform
# enable_nat_gateway      = true
map_public_ip_on_launch = true
```

I reduced my task and container's CPU and memory, and use public subnets with assigning public IPs for my ECS tasks (`subnet_ids` and `assign_public_ip`). This should save \~$9.50 per month on vCPU and \~$7.50 per month on memory:

```terraform
services = {
  (local.module) = {
    # cpu    = 512
    # memory = 2048
    cpu    = 256
    memory = 1024

    # subnet_ids       = module.vpc.private_subnets
    subnet_ids       = module.vpc.public_subnets
    assign_public_ip = true

    container_definitions = {
      (local.module) = {
        # cpu       = 256
        # memory    = 512
        cpu       = 128
        memory    = 384
      }
    }
  }
}
```

Also, I reduced the number of availability zones from 3 to 2 in my VPC module to save some costs on data transfer between AZs. Note that there is a limitation that ALB requires at least 2 AZs (see [AWS Application Load Balancers Availability Zone Subnets](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html#:~:text=You%20must%20select%20at%20least,attempting%20to%20establish%20a%20connection.)):

```terraform
# azs             = ["${var.aws_region}a", "${var.aws_region}b", "${var.aws_region}c"]
# private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
# public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]
azs             = ["${var.aws_region}a", "${var.aws_region}b"]
private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]
```

Additionally, I upgraded the ECS Fargate capacity provider strategy. With at least one FARGATE provider, the 2-minute window seems acceptable for a personal website:

```terraform
default_capacity_provider_strategy = {
  FARGATE = {
    base   = 1
    # weight = 50
    weight = 25
  }
  FARGATE_SPOT = {
    # weight = 50
    weight = 75
  }
}
```

While these approaches significantly reduce costs, they do have security implications. The ECS tasks now have public IPs and access ECR/CloudWatch Logs over the internet instead of through private VPC endpoints. I have several mitigations in place:

- **IAM Policies**: The `terraform-aws-modules/ecs/aws` module already automatically creates IAM roles with least privilege for ECS tasks to access ECR and CloudWatch Logs
- **Security Groups**: Only the ALB can communicate with the ECS tasks (no direct internet access to tasks)
- **CloudFront** sits in front of the ALB, providing DDoS protection and caching

:::note
I have to say, I really dislike the idea of allowing public access to ECR and CloudWatch Logs, but the price of following the best practice is just way more than I expected for a personal website. I will probably change this back after I have more containerized applications running in my AWS account and can justify the cost of VPC endpoints or NAT gateways.
:::

:::warning
I do feel the website is much slower after applying the changes, and I notice that the CPU and Memory utilization of the ECS tasks on CloudWatch Metrics are much higher than before. I might need to monitor the performance and consider scaling up the resources or optimizing caches.

I believe using private subnets with VPC endpoints or NAT gateways would likely reduce the latency, but it will be my last choice due to the cost.
:::
