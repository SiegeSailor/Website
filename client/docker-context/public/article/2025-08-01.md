I developed a Next.js application running in a Docker container on a purpose-built ARM64 board with WebKit `cog` as the rendering engine. It was working fine on the board, AMD64 Linux, and ARM64 macOS. However, after adding further MongoDB features and some refactoring utilizing Next.js server actions, the Next.js application was then not able to make database operations. The only error message I could see was `Syntax Error: JSON.parse`.

It often experienced something like lost connections without reason and resumed connections without reason as well. Retrying the operations would eventually succeed, but it wasn't about the number it retired but the time it waited. For example, in around 10 seconds after a lost connection, all the retires would still fail, but after that, all the operations would succeed for a while.

The application was running in a Docker container with the following relevant software versions:

- **Base Image**: [ubuntu:22.04](https://hub.docker.com/layers/library/ubuntu/22.04/images/sha256-965fbcae990b0467ed5657caceaec165018ef44a4d2d46c7cdea80a9dff0d1ea?context=explore)
- **Docker Engine**: [20.10.17](https://docs.docker.com/engine/release-notes/20.10/#201017)
- **MongoDB**: [4.4.15](https://www.mongodb.com/docs/v4.4/reference/configuration-options/#configuration-file)
- **Next.js**: [15.3.4](https://nextjs.org/blog/next-15-3)
- **WebKit**: [2.48.0](https://wpewebkit.org/reference/stable/wpe-webkit-2.0/class.Settings.html)

## Problem Analysis

The issue appeared after adding MongoDB relevant features and some refactoring utilizing Next.js server actions. Here I list the previously working setups with MongoDB:

- Connect to the MongoDB server in the server component
- Call MongoDB operations through server actions passed from server components to client components
- No transactions

After the changes explained in the following sections, the application experienced issues with database operations. The only clue was the following message showing on my remote SSH terminal that logs the Docker container output:

```plaintext
⨯ SyntaxError: Unexpected end of JSON input
    at JSON.parse (<anonymous>) {
  digest: '2367858545'
}
```

### Attempted Solutions

I tried several approaches to resolve the issue:

1. Minimized the possible performance MongoDB impact:
   - Used `zstd` for MongoDB compression instead of `snappy`
   - Increased the timeout, connection, and number of listener values for MongoDB and Mongoose
   - Disabled replica sets
   - Removed transactions in Mongoose operations
2. Ensured objects passed to and from server actions are serializable
3. Added `manifest.json` to prevent Next.js from fetching metadata files
4. Prevented Next.js all pages from being dynamically rendered:
   - Set `dynamic` to `force-static`
   - Set `revalidate` to `false`
   - Set `fetchCache` to `force-no-store`
5. Turned possibly relevant Next.js configuration off:
   - Disabled `logging`
   - Increased page data, header size, and buffer length limits
   - Allow all CORS headers
6. Created Next.js HTTP routes to handle MongoDB operations instead of using server actions

The last approach worked. I was wondering why the network tab on my Chrome developer tools showed a lot of requests, then I figured out the server action calls were actually HTTP calls underneath. I then confirmed it in the [Next.js Server Actions and Mutations](https://nextjs.org/docs/14/app/building-your-application/data-fetching/server-actions-and-mutations). Overall, the core issue was that the Next.js application wasn't able to find itself on `cog` through server actions or fetching requests with relative URLs such as `/api/user`. I had to specify the full URL like `http://127.0.0.1:300/api/user` to make it work. This was not required on AMD64 Linux and ARM64 macOS.

:::fact
Behind the scenes, actions use the `POST` method, and only this HTTP method can invoke them.
:::

I doubted that Next.js on Cog had a request implementation race condition flow, where `fetch` call completed synchronously, and `cog`'s networking stack asynchronously constructs the actual HTTP request, so the HTTP requests were sent before the request body was fully attached. I discovered this by putting a delay before the fetch, which enforces the fetch to execute in a new macrotask cycle, giving `cog`'s internal networking stack time to complete its setup.

### Debugging Challenges

While working on the attempted solutions, there were factors that made the debugging process challenging:

- The issue only appeared on the purpose-built ARM64 board with `cog`
  - Running Next.js with `next dev` would consume too much resources and the board would become unresponsive
    - Hence, the error messages were replaced with a digest code, which I found no logs about it
  - There was no direct access to the console logs. This was solved by adding the `--enable-write-console-messages-to-stdout` flag to `cog` and redirecting the logs to a file
- Server action errors were not catchable
  - Next.js client components couldn't catch errors thrown in server actions. See the [GitHub Conversation](https://github.com/vercel/next.js/discussions/81912) I proposed
  - `instrumentation.js` doesn't capture the server errors
  - Even with `middleware.js`, I couldn't see useful information, as the requests were **empty** while the errors happened
- There were multiple issues happening at the same time, such as [MongoDB Misleading Message](/blog/2025-06-26) and [Cog Performance Issues](/blog/2025-09-14), causing me suspecting other parts of the system
